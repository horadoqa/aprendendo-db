🧩 O que é modelagem de dados?

Modelagem de dados é o processo de definir como as informações de uma aplicação serão organizadas e relacionadas.

Em outras palavras, antes de sair criando coleções e documentos, precisamos decidir:

  • Quais informações precisam ser armazenadas?
  • Quais informações pertencem ao mesmo contexto?
  • Quais dados são consultados juntos?
  • Quais dados mudam com frequência?
  • Quais relacionamentos existem entre os dados?
  • Quais consultas a aplicação realizará?
No MongoDB, a modelagem deve ser orientada principalmente pelo acesso aos dados.

Ou seja, não pensamos apenas em como os dados são organizados, mas também em como a aplicação precisa consultá-los.

🛒 Exemplo: uma loja virtual

Imagine que estamos criando uma loja virtual.

Precisamos armazenar informações sobre:

👤

Clientes

Nome, e-mail, telefone e endereço.

📦

Produtos

Nome, preço, categoria e estoque.

🛍️

Pedidos

Produtos comprados, quantidade, valores e data.

💳

Pagamentos

Informações relacionadas ao pagamento e seu status.

🧠 Primeiro princípio: pense nas consultas

Em bancos relacionais, é comum começar pensando bastante na estrutura das entidades e relacionamentos.

No MongoDB, precisamos também pensar:

"Como minha aplicação vai buscar esses dados?"

Imagine que a aplicação frequentemente exibe: 

Pedido
├── cliente
├── produtos
├── endereço de entrega
└── pagamento

Talvez faça sentido armazenar determinadas informações relacionadas ao pedido dentro do próprio documento do pedido.

📦 Documentos incorporados

Uma das principais estratégias de modelagem no MongoDB é o uso de documentos incorporados, também conhecidos como embedded documents.

Nesse modelo, informações relacionadas ficam dentro do documento principal. 

{
    nome: "Ana",
    email: "ana@email.com",

    endereco: {
        rua: "Rua das Flores",
        numero: 100,
        cidade: "Rio de Janeiro",
        estado: "RJ"
    }
}

O endereço faz parte do documento do cliente.

✅ Vantagens dos documentos incorporados

🚀 Menos consultas

Informações relacionadas podem ser recuperadas junto com o documento principal.

📦 Dados juntos

Informações que pertencem ao mesmo contexto ficam próximas.

🧠 Modelo natural

A estrutura do documento pode representar diretamente o objeto utilizado pela aplicação.

🤔 Quando devemos incorporar?

Incorporar dados costuma fazer sentido quando:

  • Os dados possuem uma relação forte com o documento principal.
  • Normalmente são consultados juntos.
  • O conjunto incorporado possui tamanho controlado.
  • Os dados não precisam ser compartilhados de maneira independente entre muitos documentos.
Exemplo:

Endereço de um cliente pode ser incorporado ao documento do cliente quando esse endereço pertence diretamente ao contexto daquele cliente.

🔗 Referências

Outra estratégia é armazenar os dados separadamente e criar uma referência entre os documentos.

Imagine: 

clientes

{
    _id: 101,
    nome: "Ana"
}

E: 

pedidos

{
    _id: 5001,
    clienteId: 101,
    total: 3500
}

O campo clienteId relaciona o pedido ao cliente.

⚖️ Embutir ou referenciar?

Situação Embutir Referenciar
Dados sempre usados juntos Geralmente adequado Pode ser desnecessário
Relação forte Geralmente adequado Pode ser utilizado
Dados compartilhados por muitos documentos Pode gerar duplicação Frequentemente adequado
Lista potencialmente muito grande Pode ser problemático Pode ser mais apropriado
Dados precisam ser atualizados independentemente Pode exigir várias atualizações Pode facilitar a centralização

🛍️ Exemplo: pedido e itens

Imagine um pedido com três produtos.

Podemos representar os itens dentro do próprio pedido: 

{
    _id: 5001,

    clienteId: 101,

    itens: [

        {
            produtoId: 10,
            nome: "Notebook",
            quantidade: 1,
            preco: 3500
        },

        {
            produtoId: 20,
            nome: "Mouse",
            quantidade: 2,
            preco: 100
        }

    ],

    total: 3700
}

Observe que o pedido possui uma lista de itens.

Uma decisão importante:

O pedido pode armazenar informações do produto necessárias para representar aquele momento da compra, mesmo que o produto original continue existindo em outra coleção.

📋 Duplicação de dados

Em bancos relacionais, frequentemente aprendemos a evitar duplicação de dados através da normalização.

No MongoDB, alguma duplicação pode ser uma decisão válida de modelagem.

Por exemplo, um pedido pode armazenar: 

{
    produtoId: 10,
    nomeProduto: "Notebook",
    precoUnitario: 3500,
    quantidade: 1
}

Mesmo que o produto também exista em uma coleção produtos.

Por quê?

Porque o pedido pode precisar preservar os dados relevantes daquela operação, como o preço praticado no momento da compra.

⚠️ Cuidado com arrays muito grandes

Incorporar dados é útil, mas não significa que devemos colocar tudo dentro de um único documento.

Imagine um usuário com milhões de comentários: 

{
    nome: "Ana",

    comentarios: [
        "...",
        "...",
        "...",
        "...",
        "...",
        "..."
    ]
}

Uma estrutura desse tipo pode crescer de forma inadequada.

Pense no crescimento dos dados.

Se uma informação relacionada pode crescer indefinidamente, talvez seja necessário considerar uma coleção separada e referências.

🔢 Relacionamento 1:N

Um relacionamento de um para muitos ocorre quando um documento está relacionado a vários outros.

Exemplo: 

Um cliente
    ↓
Muitos pedidos

Uma possibilidade seria: 

{
    _id: 101,
    nome: "Ana"
}

E os pedidos: 

{
    _id: 5001,
    clienteId: 101
}

{
    _id: 5002,
    clienteId: 101
}

{
    _id: 5003,
    clienteId: 101
}

🔀 Relacionamento N:N

Um relacionamento muitos para muitos acontece quando vários documentos podem estar relacionados a vários outros.

Um exemplo clássico é: 

Alunos
   ↕
Cursos

Um aluno pode participar de vários cursos.

Um curso pode possuir vários alunos.

Nesse tipo de cenário, referências podem ser uma alternativa importante de modelagem.

🔎 Modele para as consultas

Considere uma aplicação que frequentemente precisa mostrar: 

Nome do cliente
+
Últimos pedidos
+
Total gasto

A modelagem deve considerar essa necessidade.

A pergunta não é apenas:

"Como representar os dados?"

Mas também:

"Como a aplicação precisa acessar esses dados?"

🧪 Dois modelos possíveis

Modelo A — incorporado 

{
    nome: "Ana",

    endereco: {
        cidade: "Rio de Janeiro",
        estado: "RJ"
    }
}

Modelo B — referência 

clientes

{
    _id: 101,
    nome: "Ana",
    enderecoId: 900
}


enderecos

{
    _id: 900,
    cidade: "Rio de Janeiro",
    estado: "RJ"
}

Os dois modelos podem representar a mesma ideia, mas possuem características diferentes.

🧠 Perguntas para escolher o modelo

  • Esses dados são acessados juntos?
  • Eles possuem uma relação forte?
  • O conjunto de dados possui tamanho controlado?
  • Os dados são compartilhados por vários documentos?
  • Eles precisam ser atualizados separadamente?
  • Quanto esses dados podem crescer?
  • Quais consultas a aplicação realizará?

❌ Erro comum: copiar regras relacionais diretamente

Um erro comum ao começar com MongoDB é tentar transformar automaticamente cada entidade de um modelo relacional em uma coleção independente.

Por exemplo: 

clientes
enderecos
telefones
pedidos
itens_pedido
pagamentos

Essa estrutura pode ser válida em determinadas situações, mas não devemos assumir que ela é obrigatoriamente a melhor forma de modelar os dados no MongoDB.

MongoDB não significa simplesmente "SQL sem tabelas".

O modelo de documentos permite tomar decisões diferentes de acordo com as necessidades da aplicação.

📄 Exemplo de documento bem estruturado 

{
    _id: 5001,

    cliente: {
        id: 101,
        nome: "Ana"
    },

    enderecoEntrega: {
        rua: "Rua das Flores",
        numero: 100,
        cidade: "Rio de Janeiro",
        estado: "RJ"
    },

    itens: [

        {
            produtoId: 10,
            nome: "Notebook",
            precoUnitario: 3500,
            quantidade: 1
        },

        {
            produtoId: 20,
            nome: "Mouse",
            precoUnitario: 100,
            quantidade: 2
        }

    ],

    total: 3700,

    status: "pago",

    criadoEm: ISODate("2026-01-10")
}

Esse documento representa o contexto de um pedido e concentra informações que podem ser necessárias para exibi-lo.

✅ Boas práticas de modelagem

🔎 Pense nas consultas

Modele considerando como os dados serão acessados.

📦 Agrupe dados relacionados

Informações que normalmente são usadas juntas podem ser candidatas à incorporação.

🔗 Use referências quando necessário

Dados compartilhados ou de crescimento elevado podem exigir outra estratégia.

📈 Pense no crescimento

Não analise apenas o estado atual dos dados.

📝 Resumindo

Modelagem de dados é o processo de decidir como as informações serão organizadas.

No MongoDB, devemos considerar não apenas os dados, mas também como a aplicação consulta esses dados.

Documentos incorporados permitem armazenar informações relacionadas dentro do documento principal.

Referências permitem relacionar documentos armazenados separadamente.

A incorporação pode ser interessante quando os dados possuem relação forte e são acessados juntos.

Referências podem ser adequadas quando os dados são compartilhados, independentes ou possuem crescimento que torna a incorporação inadequada.

Não existe uma única estrutura correta para todos os sistemas. A decisão depende dos requisitos, consultas, crescimento e comportamento da aplicação.
