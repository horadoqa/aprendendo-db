📄 O que é um documento?

Um documento MongoDB é uma estrutura formada por campos e valores. 

{
    "nome": "Ana Silva",
    "idade": 25,
    "ativo": true
}

Nesse exemplo temos três campos:

  • nome
  • idade
  • ativo

Cada campo possui um valor correspondente.

🏷️ Campos e valores

Um campo possui um nome e um valor. 

{
    "nome": "Carlos"
}

Podemos interpretar dessa forma:

Campo Valor Tipo
nome "Carlos" String
idade 30 Número
ativo true Boolean

🔤 Strings

Strings representam textos. 

{
    "nome": "Maria",
    "email": "maria@email.com",
    "cidade": "Rio de Janeiro"
}

Strings são utilizadas para informações como nomes, e-mails, endereços, descrições e outros textos.

🔢 Números

Números podem representar valores como idade, quantidade, preço ou pontuação. 

{
    "idade": 25,
    "saldo": 1500.50,
    "quantidade": 10
}
Uma atenção importante:

Valores numéricos devem ser armazenados como números quando pretendemos realizar operações matemáticas ou comparações numéricas.

✅ Booleanos

Booleanos representam dois estados: true ou false. 

{
    "ativo": true,
    "verificado": false
}

São úteis para representar situações como:

  • Usuário ativo ou inativo.
  • E-mail verificado ou não verificado.
  • Produto disponível ou indisponível.

📚 Arrays

Um array permite armazenar uma lista de valores. 

{
    "nome": "Ana",

    "linguagens": [

        "JavaScript",

        "Python",

        "SQL"

    ]
}

Nesse caso, o campo linguagens possui três valores.

Imagine:

Um usuário pode possuir vários telefones, vários endereços ou várias habilidades.

Um array pode representar essas listas dentro do documento.

🧩 Arrays de objetos

Um array também pode armazenar objetos. 

{
    "nome": "Ana",

    "enderecos": [

        {
            "tipo": "residencial",
            "cidade": "Rio de Janeiro"
        },

        {
            "tipo": "comercial",
            "cidade": "Niterói"
        }

    ]
}

Agora cada item do array possui seus próprios campos.

Esse recurso é muito importante no MongoDB.

Ele permite representar estruturas complexas de forma natural dentro de um documento.

📦 Documentos aninhados

Também podemos colocar um objeto diretamente dentro de outro objeto. 

{
    "nome": "João",

    "endereco": {

        "rua": "Rua A",

        "numero": 100,

        "cidade": "São Paulo",

        "estado": "SP"

    }
}

O campo endereco contém outro objeto.

Observe a estrutura:

Documento → endereço → cidade

🆔 ObjectId e o campo _id

O MongoDB utiliza o campo _id para identificar cada documento de forma única dentro de uma coleção. 

{
    "_id": ObjectId("65a123456789abcdef123456"),

    "nome": "Ana Silva",

    "email": "ana@email.com"
}

Quando o MongoDB gera automaticamente esse identificador, ele normalmente utiliza um valor do tipo ObjectId.

Regra importante:

Dois documentos da mesma coleção não podem possuir o mesmo valor de _id.

🗃️ O que é uma coleção?

Uma coleção agrupa documentos relacionados.

Em uma aplicação de comércio eletrônico, poderíamos ter: 

loja
│
├── clientes
│
├── produtos
│
├── pedidos
│
└── pagamentos

Cada coleção possui uma finalidade.

clientes

Documentos que representam clientes.

produtos

Documentos que representam produtos.

pedidos

Documentos que representam pedidos.

pagamentos

Documentos relacionados aos pagamentos.

🔀 Documentos podem ter estruturas diferentes?

Em bancos documentais como MongoDB, documentos da mesma coleção podem ter estruturas diferentes. 

{
    "nome": "Ana",
    "email": "ana@email.com"
}


{
    "nome": "João",
    "email": "joao@email.com",
    "telefone": "99999-9999"
}

O segundo documento possui um campo adicional: telefone.

Mas flexibilidade não significa ausência de regras.

Uma aplicação pode definir validações e padrões para garantir a qualidade dos dados.

Uma estrutura flexível deve ser utilizada conscientemente.

🔗 Embutir ou referenciar dados?

Ao modelar documentos MongoDB, uma decisão importante é escolher entre embutir informações ou utilizar referências.

Dados embutidos 

{
    "nome": "Ana",

    "endereco": {

        "cidade": "Rio de Janeiro",

        "estado": "RJ"

    }
}

O endereço está armazenado dentro do documento do cliente.

Referência 

{
    "clienteId": ObjectId("..."),
    "nome": "Pedido #1001"
}

Nesse caso, o documento pode utilizar um identificador para apontar para outro documento.

Não existe uma regra única.

A decisão depende de como os dados são utilizados, consultados e atualizados pela aplicação.

📦 Quando pensar em dados embutidos?

Dados embutidos podem ser interessantes quando as informações normalmente são acessadas juntas. 

{
    "nome": "Ana",

    "contato": {

        "email": "ana@email.com",

        "telefone": "99999-9999"

    }
}

O contato faz parte das informações do cliente e pode ser lido junto com ele.

🔗 Quando pensar em referências?

Referências podem ser interessantes quando uma informação é compartilhada por vários documentos ou possui vida própria. 

{
    "produtoId": ObjectId("..."),

    "quantidade": 2
}

O pedido pode guardar uma referência para o produto em vez de duplicar todas as informações do produto.

Pense sempre nos padrões de acesso.

A modelagem NoSQL costuma começar pelas perguntas que a aplicação precisa responder e pela forma como os dados serão acessados.

🛒 Exemplo completo

Podemos representar um cliente de uma loja desta forma: 

{
    "_id": ObjectId("65a123..."),

    "nome": "Ana Silva",

    "email": "ana@email.com",

    "idade": 25,

    "ativo": true,

    "endereco": {

        "cidade": "Rio de Janeiro",

        "estado": "RJ"

    },

    "interesses": [

        "Tecnologia",

        "Banco de Dados",

        "Programação"

    ]

}

Esse único documento possui:

  • Um identificador.
  • Informações textuais.
  • Um número.
  • Um booleano.
  • Um objeto aninhado.
  • Um array.

🗂️ Uma coleção com vários documentos

Uma coleção pode conter diversos documentos: 

clientes

┌─────────────────────────────┐
│ Documento 1                 │
│ nome: "Ana"                 │
│ email: "ana@email.com"      │
└─────────────────────────────┘

┌─────────────────────────────┐
│ Documento 2                 │
│ nome: "João"                │
│ email: "joao@email.com"     │
└─────────────────────────────┘

┌─────────────────────────────┐
│ Documento 3                 │
│ nome: "Maria"               │
│ email: "maria@email.com"    │
└─────────────────────────────┘

Todos esses documentos pertencem à coleção clientes.

🧠 Collection × Document

Conceito Função Exemplo
Collection Agrupar documentos relacionados. clientes
Document Representar uma informação. { nome: "Ana" }

🔄 Collection × Table

Para facilitar o aprendizado, podemos estabelecer uma comparação inicial: 

SQL                         MongoDB

Tabela                      Coleção
   │                           │
   ├── Linha                   ├── Documento
   ├── Linha                   ├── Documento
   └── Linha                   └── Documento

Porém, não devemos tratar os dois conceitos como equivalentes em todos os aspectos.

Por quê?

O modelo relacional é baseado em relações, tabelas, linhas, colunas e restrições.

O modelo documental trabalha com documentos que podem possuir estruturas aninhadas, arrays e diferentes formas de modelagem.

✅ Boas práticas iniciais

🏷️ Use nomes claros

Prefira nomes que representem claramente o significado do campo.

📐 Pense na estrutura

Flexibilidade não significa criar documentos sem organização.

🔎 Pense nas consultas

A forma como os dados serão consultados influencia a modelagem.

🧩 Evite duplicação desnecessária

Analise cuidadosamente quando embutir ou referenciar informações.

⚠️ Erros comuns

❌ "MongoDB não possui estrutura"

Documentos possuem estrutura e podem possuir regras de validação.

❌ "Todo dado deve ser embutido"

Existem situações em que referências são mais adequadas.

❌ "Todo dado deve ser separado"

Dados que são acessados juntos podem, dependendo do caso, ser embutidos.

❌ "Flexível significa bagunçado"

Uma boa modelagem continua exigindo organização e regras.

📝 Resumindo

Um documento MongoDB é formado por campos e valores.

Uma coleção agrupa documentos relacionados.

Documentos podem conter strings, números, booleanos, arrays, objetos, datas e outros tipos.

Documentos podem possuir estruturas aninhadas.

Arrays podem armazenar valores ou objetos.

O campo _id identifica cada documento de maneira única dentro de uma coleção.

Na modelagem NoSQL, é importante considerar como os dados serão acessados antes de decidir entre embutir ou referenciar informações.
