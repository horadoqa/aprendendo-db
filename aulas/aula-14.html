AULA 14 • ÍNDICES E PERFORMANCE

Índices e Otimização de Consultas SQL

Aprenda como os índices funcionam, como analisar consultas SQL e como identificar oportunidades de melhoria de performance.

Objetivos da aula

À medida que uma aplicação cresce, suas tabelas podem armazenar milhares, milhões ou até bilhões de registros.

Uma consulta que funciona rapidamente com 100 registros pode apresentar um comportamento completamente diferente quando a tabela cresce.

Performance

Entender por que algumas consultas são mais rápidas que outras.

📇

Índices

EXPLAIN

Por que uma consulta pode ficar lenta?

Imagine uma tabela com milhões de clientes. 

clientes

id
nome
email
cidade
data_cadastro

Agora imagine que precisamos encontrar um cliente pelo endereço de e-mail: 

SELECT *
FROM clientes
WHERE email = 'ana@email.com';

Se o banco precisar verificar uma enorme quantidade de registros para encontrar o resultado, a consulta pode se tornar custosa.

É aqui que os índices entram.

Um índice pode fornecer uma estrutura auxiliar que permite ao SGBD localizar determinados dados de maneira mais eficiente.

O que é um índice?

Um índice é uma estrutura de dados mantida pelo SGBD para acelerar determinadas operações de acesso aos dados.

Analogia:

Imagine um livro com 1.000 páginas.

Sem um índice, para encontrar um determinado assunto você poderia precisar procurar página por página.

Com um índice, você pode localizar rapidamente a página onde o assunto aparece.

O conceito é semelhante no banco de dados: uma estrutura adicional pode ajudar o SGBD a encontrar determinadas linhas sem precisar examinar toda a tabela.

Criando um índice

Uma sintaxe comum em bancos relacionais é: 

CREATE INDEX idx_clientes_email
ON clientes (email);

Nesse exemplo:

  • CREATE INDEX cria o índice.
  • idx_clientes_email é o nome escolhido para o índice.
  • clientes é a tabela.
  • email é a coluna indexada.

Antes e depois do índice

🐢

Sem índice

Dependendo da consulta e do plano escolhido, o SGBD pode precisar examinar muitas linhas.

🚀

Com índice

O SGBD pode utilizar a estrutura indexada para localizar os dados de maneira mais eficiente.

Importante:

Criar um índice não garante automaticamente que toda consulta ficará mais rápida.

O otimizador do SGBD decide se o índice é adequado para determinado plano de execução.

B-tree

Um dos tipos de índice mais conhecidos em bancos relacionais é o baseado em B-tree.

Ele é adequado para diversos tipos de operações, incluindo muitos casos de:

  • Comparações de igualdade.
  • Ordenação.
  • Consultas por intervalo.
  • Operadores como >, <, >= e <=. 
SELECT *
FROM produtos
WHERE preco > 100;

A estrutura exata e os tipos disponíveis dependem do SGBD.

Índices Hash

Índices baseados em hash podem ser adequados para determinados tipos de busca por igualdade. 

WHERE email = 'ana@email.com'
Atenção:

Hash não deve ser entendido como "sempre mais rápido". As vantagens dependem da implementação, do SGBD, da consulta e do tipo de operação.

Índice composto

Um índice também pode utilizar mais de uma coluna. 

CREATE INDEX idx_clientes_cidade_nome
ON clientes (cidade, nome);

Esse índice possui duas colunas: 

cidade
nome

A ordem das colunas do índice é importante para determinar quais consultas podem aproveitá-lo melhor.

Regra prática:

Não pense em índices compostos apenas como "um índice com várias colunas".

A ordem das colunas influencia o conjunto de consultas para as quais o índice pode ser útil.

Exemplo de índice composto 

CREATE INDEX idx_pedidos_cliente_data
ON pedidos (cliente_id, data_pedido);

Esse índice pode ser interessante para consultas relacionadas a um determinado cliente e sua data de pedido. 

SELECT *
FROM pedidos
WHERE cliente_id = 10
ORDER BY data_pedido;

Porém, o benefício concreto depende do plano de execução, da distribuição dos dados e das características do SGBD.

Índice UNIQUE

Um índice UNIQUE ajuda a garantir que os valores indexados não se repitam, de acordo com as regras do SGBD. 

CREATE UNIQUE INDEX idx_usuarios_email
ON usuarios (email);

Nesse caso, não podemos ter dois registros com o mesmo valor de email, respeitando as regras específicas de valores nulos do SGBD.

Em muitos projetos, essa regra é expressa por uma UNIQUE CONSTRAINT, que também pode levar o SGBD a criar ou utilizar uma estrutura de índice para garantir a unicidade.

E a Primary Key?

Uma PRIMARY KEY identifica unicamente os registros de uma tabela. 

CREATE TABLE usuarios (

    id INTEGER PRIMARY KEY,

    nome VARCHAR(100)

);

A forma como a restrição é implementada depende do SGBD, mas é comum que exista uma estrutura indexada associada à chave primária.

Índices também possuem custo

Um erro comum é imaginar que devemos criar índices em todas as colunas.

💾

Espaço

Índices ocupam espaço adicional de armazenamento.

✏️

Escritas

INSERT, UPDATE e DELETE podem precisar atualizar os índices.

🧩

Manutenção

Muitos índices aumentam a complexidade da estrutura do banco.

⚖️

Equilíbrio

É necessário equilibrar velocidade de leitura e custo das operações de escrita.

Seletividade

A seletividade está relacionada à capacidade de uma condição filtrar uma pequena parte dos registros.

Imagine uma tabela com 10 milhões de usuários.

Uma coluna como: 

email

normalmente possui muitos valores distintos.

Já uma coluna como: 

sexo

pode possuir poucos valores distintos, dependendo do modelo utilizado.

Ideia importante:

O fato de uma coluna possuir um índice não significa que o otimizador sempre encontrará vantagem em utilizá-lo.

EXPLAIN

Uma das ferramentas mais importantes para entender performance de consultas é o comando EXPLAIN.

Ele permite visualizar informações sobre o plano de execução escolhido pelo SGBD. 

EXPLAIN
SELECT *
FROM clientes
WHERE email = 'ana@email.com';
Importante:

EXPLAIN normalmente mostra o plano estimado. Para medir a execução real, muitos SGBDs oferecem recursos adicionais, como EXPLAIN ANALYZE.

EXPLAIN ANALYZE

Em SGBDs que oferecem esse recurso, EXPLAIN ANALYZE executa a consulta e apresenta informações observadas durante a execução. 

EXPLAIN ANALYZE
SELECT *
FROM pedidos
WHERE cliente_id = 10;

No PostgreSQL, por exemplo, o resultado pode apresentar informações como:

  • Tipo de operação executada.
  • Estimativas de custo.
  • Quantidade estimada e real de linhas.
  • Tempo de execução.
  • Uso de índices.

Sequential Scan

Um Sequential Scan, também chamado de varredura sequencial, ocorre quando o SGBD percorre as páginas da tabela para encontrar os registros relevantes.

Importante:

Sequential Scan não significa necessariamente que a consulta está mal otimizada.

Para tabelas pequenas ou consultas que precisam retornar uma grande parte dos registros, uma varredura sequencial pode ser uma escolha adequada.

Index Scan

Em um Index Scan, o SGBD utiliza um índice para localizar os registros necessários. 

CREATE INDEX idx_clientes_email
ON clientes (email);

Uma consulta por e-mail pode então ter um plano que utilize esse índice, dependendo das estatísticas e do custo estimado.

Index Only Scan

Alguns SGBDs, como o PostgreSQL, possuem estratégias nas quais determinadas consultas podem obter os dados necessários diretamente a partir do índice, quando todas as informações relevantes estão disponíveis nele e as demais condições são satisfeitas.

Ideia:

Se a consulta precisa apenas de informações presentes no índice, pode ser possível evitar parte do acesso à tabela.

Evite usar SELECT * sem necessidade

Compare: 

SELECT *
FROM clientes
WHERE id = 10;

com: 

SELECT nome, email
FROM clientes
WHERE id = 10;

Selecionar somente as colunas necessárias pode tornar o código mais claro e, em determinados cenários, reduzir a quantidade de dados transferidos ou processados.

Mas atenção:

Evitar SELECT * é uma boa prática de clareza e controle de dados, mas não significa que essa mudança, sozinha, sempre produzirá uma grande melhoria de performance.

Use filtros adequados

Sempre que possível, faça a consulta retornar somente os dados necessários. 

SELECT nome, email
FROM clientes
WHERE cidade = 'Rio de Janeiro';

O banco ainda precisará executar o plano escolhido, mas reduzir o conjunto de dados trabalhado pode ser importante para a aplicação.

Cuidado com funções nas colunas

Algumas expressões podem dificultar o aproveitamento de um índice, dependendo do SGBD e do índice disponível.

Por exemplo: 

SELECT *
FROM clientes
WHERE LOWER(email)
      = 'ana@email.com';

Uma possibilidade, dependendo do SGBD, é utilizar um índice apropriado para a expressão ou alterar a estratégia de armazenamento e consulta.

Regra importante:

Não altere uma consulta apenas por uma "regra de internet". Analise o plano de execução e meça o comportamento no ambiente real.

LIKE e índices

Consultas com LIKE podem ter comportamentos diferentes dependendo do padrão utilizado, do SGBD e do tipo de índice. 

SELECT *
FROM clientes
WHERE nome LIKE 'Ana%';

Um padrão que começa com um valor conhecido pode ter oportunidades de otimização diferentes de um padrão que começa com um curinga. 

LIKE '%Ana%'

O comportamento exato depende do SGBD, collation, operador, índice e configuração utilizada.

ORDER BY e índices

Índices também podem ser relevantes para consultas que precisam ordenar resultados. 

SELECT *
FROM produtos
ORDER BY preco;

Um índice adequado pode, em determinados cenários, ajudar o SGBD a produzir os dados na ordem necessária.

Porém, novamente, a decisão depende do plano de execução e do custo estimado.

LIMIT e paginação

Quando a aplicação precisa mostrar apenas uma parte dos resultados, podemos utilizar mecanismos de paginação. 

SELECT id, nome
FROM clientes
ORDER BY id
LIMIT 20;

Para conjuntos muito grandes, paginação baseada em um valor de referência pode ser uma alternativa interessante. 

SELECT id, nome
FROM clientes
WHERE id > 1000
ORDER BY id
LIMIT 20;
Importante:

O uso de OFFSET em páginas muito profundas pode se tornar custoso em alguns cenários, porque o banco pode precisar percorrer e descartar muitas linhas antes de chegar ao resultado desejado.

OFFSET 

SELECT id, nome
FROM clientes
ORDER BY id
LIMIT 20
OFFSET 100000;

Dependendo do banco e do plano, consultar páginas muito distantes pode exigir trabalho significativo.

Uma alternativa é utilizar paginação baseada em cursor ou em uma coluna ordenada. 

SELECT id, nome
FROM clientes
WHERE id > 100000
ORDER BY id
LIMIT 20;

Performance em JOINs

Consultas com JOIN podem envolver grandes quantidades de dados. 

SELECT
    p.id,
    p.data_pedido,
    c.nome
FROM pedidos p
JOIN clientes c
    ON c.id = p.cliente_id;

Colunas utilizadas frequentemente em relacionamentos podem precisar de índices apropriados, dependendo das consultas e do plano escolhido.

Um JOIN não é necessariamente lento. O importante é analisar o plano de execução, cardinalidade, índices e quantidade de dados envolvidos.

O problema N+1

O problema N+1 acontece quando a aplicação executa uma consulta para obter uma lista e depois executa uma nova consulta para cada item dessa lista.

Por exemplo: 

1 consulta → buscar pedidos

+ 100 consultas → buscar cliente de cada pedido

= 101 consultas
Possível alternativa:

Em muitos casos, podemos utilizar um JOIN ou outra estratégia de carregamento de dados para reduzir a quantidade de viagens ao banco.

Estatísticas e otimizador

O SGBD utiliza estatísticas sobre os dados para estimar o custo de diferentes planos de execução.

📊

Estatísticas

Informações sobre distribuição e quantidade dos dados.

🧠

Otimizador

Compara estratégias possíveis para executar a consulta.

🗺️

Plano

Define como a consulta será executada.

Se as estatísticas estiverem desatualizadas, o otimizador pode fazer estimativas menos precisas.

Otimização não é adivinhação

Uma das principais ideias desta aula é:

Não otimize apenas pelo que parece mais rápido. Meça e analise.

Uma boa estratégia é:

  1. Identificar uma consulta lenta.
  2. Medir o comportamento atual.
  3. Analisar o plano de execução.
  4. Identificar o gargalo.
  5. Fazer uma alteração.
  6. Executar novamente a medição.
  7. Comparar os resultados.

Processo de otimização

1️⃣

Medir

Descobrir quanto tempo a consulta realmente está levando.

2️⃣

Analisar

Examinar o plano e identificar operações custosas.

3️⃣

Alterar

Criar índice, modificar consulta ou ajustar a estrutura.

4️⃣

Medir novamente

Confirmar se a mudança realmente melhorou o cenário.

Exemplo completo

Imagine uma tabela de pedidos: 

pedidos

id
cliente_id
data_pedido
status
valor

A aplicação realiza frequentemente: 

SELECT *
FROM pedidos
WHERE cliente_id = 10
ORDER BY data_pedido DESC;

Uma possibilidade seria estudar um índice composto: 

CREATE INDEX idx_pedidos_cliente_data
ON pedidos (cliente_id, data_pedido);

Depois, podemos comparar o plano de execução antes e depois da alteração.

Processo correto:

Não basta criar o índice. Precisamos verificar se ele realmente foi utilizado e se houve melhoria mensurável.

Quando não criar um índice?

Um índice pode não ser interessante quando:

  • A tabela é muito pequena e uma varredura completa é suficientemente barata.
  • A coluna possui baixa utilidade para as consultas realizadas.
  • O índice não é utilizado pelos planos relevantes.
  • O custo adicional nas operações de escrita supera o benefício obtido nas leituras.
  • Já existe outro índice que atende às consultas necessárias.
Importante:

Não existe uma quantidade universal de índices que seja "ideal" para todas as aplicações.

Checklist de performance

  • 🔍 A consulta realmente está lenta?
  • 🔍 Qual é o plano de execução?
  • 🔍 O filtro utiliza uma coluna adequada?
  • 🔍 Existe um índice relevante?
  • 🔍 O índice realmente é utilizado?
  • 🔍 O índice possui uma ordem adequada?
  • 🔍 A consulta está retornando dados demais?
  • 🔍 Existe um problema de N+1?
  • 🔍 As estatísticas estão atualizadas?
  • 🔍 A alteração melhorou o desempenho depois de medida?

Resumindo

Um índice é uma estrutura auxiliar criada para tornar determinadas operações de acesso aos dados mais eficientes.

Índices podem acelerar consultas, mas também ocupam espaço e aumentam o custo de determinadas operações de escrita.

O otimizador escolhe um plano de execução com base em estimativas de custo e informações disponíveis.

EXPLAIN ajuda a entender o plano escolhido pelo SGBD.

Otimização deve ser baseada em medição e análise, não apenas em suposições.
