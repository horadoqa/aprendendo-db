CRUD: as quatro operações fundamentais

Uma grande parte das aplicações realiza quatro tipos básicos de operações sobre os dados.

🟢 CREATE

Criar novos registros. 

INSERT INTO usuarios
(nome, email)
VALUES
('Ana', 'ana@email.com');

🔵 READ

Consultar registros. 

SELECT *
FROM usuarios;

🟡 UPDATE

Alterar registros existentes. 

UPDATE usuarios
SET nome = 'Maria'
WHERE id = 1;

🔴 DELETE

Remover registros. 

DELETE FROM usuarios
WHERE id = 1;

SELECT: consultando dados

O comando SELECT é uma das operações mais importantes do SQL. 

SELECT
    nome,
    email
FROM clientes;

Podemos adicionar filtros: 

SELECT
    nome,
    email
FROM clientes
WHERE cidade = 'Rio de Janeiro';

E também ordenar: 

SELECT
    nome,
    email
FROM clientes
WHERE cidade = 'Rio de Janeiro'
ORDER BY nome;

🔗 JOIN: relacionando tabelas

Em bancos relacionais, os dados normalmente são distribuídos entre diferentes tabelas.

Por exemplo: 

clientes

id
nome


pedidos

id
cliente_id
valor

Podemos relacionar essas informações utilizando JOIN. 

SELECT
    clientes.nome,
    pedidos.valor
FROM clientes

JOIN pedidos
    ON pedidos.cliente_id = clientes.id;
Ideia fundamental:

O JOIN permite combinar informações relacionadas que estão armazenadas em diferentes tabelas.

📊 GROUP BY e agregações

SQL também permite realizar cálculos sobre conjuntos de registros.

Algumas funções importantes:

  • COUNT() — quantidade de registros.
  • SUM() — soma.
  • AVG() — média.
  • MIN() — menor valor.
  • MAX() — maior valor. 
SELECT
    cliente_id,
    COUNT(*) AS quantidade_pedidos
FROM pedidos
GROUP BY cliente_id;

Podemos ainda filtrar grupos utilizando HAVING: 

SELECT
    cliente_id,
    COUNT(*) AS quantidade
FROM pedidos
GROUP BY cliente_id
HAVING COUNT(*) > 5;

Subconsultas

Uma consulta SQL pode utilizar outra consulta como parte da sua operação. 

SELECT nome
FROM clientes
WHERE id IN (

    SELECT cliente_id
    FROM pedidos
    WHERE valor > 1000

);

Subconsultas podem ser úteis, mas também é importante conhecer outras estratégias, como JOINs e CTEs, dependendo do problema.

CTE — Common Table Expression

Uma CTE permite criar uma consulta temporária dentro de outra consulta utilizando a cláusula WITH. 

WITH pedidos_grandes AS (

    SELECT *
    FROM pedidos
    WHERE valor > 1000

)

SELECT *
FROM pedidos_grandes;

CTEs podem ajudar na organização e legibilidade de consultas mais complexas.

🔒 Constraints

Constraints são regras utilizadas para garantir a integridade dos dados.

PRIMARY KEY

Identifica unicamente cada registro.

FOREIGN KEY

Representa um relacionamento entre tabelas.

UNIQUE

Impede duplicidade conforme a regra definida.

NOT NULL

Impede valores nulos naquela coluna.

CHECK

Permite definir uma condição que os dados precisam respeitar.

🧩 Modelagem de dados

Antes de escrever consultas, precisamos pensar em como os dados serão organizados.

Em um modelo relacional, normalmente identificamos:

  • Entidades.
  • Atributos.
  • Relacionamentos.
  • Chaves primárias.
  • Chaves estrangeiras.
  • Regras de integridade.
Exemplo:

Um sistema de vendas pode possuir as entidades Cliente, Produto e Pedido.

O pedido pode estar relacionado a um cliente e possuir vários produtos.

Normalização

A normalização é um conjunto de princípios utilizados para organizar os dados e reduzir determinados tipos de redundância e anomalias.

Entre os conceitos estudados estão:

  • 1ª Forma Normal.
  • 2ª Forma Normal.
  • 3ª Forma Normal.

Normalizar não significa simplesmente "separar tudo em várias tabelas".

É necessário entender dependências e regras do domínio da aplicação.

💳 Transações

Uma transação agrupa operações que devem ser tratadas como uma unidade lógica. 

BEGIN;

UPDATE contas
SET saldo = saldo - 100
WHERE id = 1;

UPDATE contas
SET saldo = saldo + 100
WHERE id = 2;

COMMIT;

Caso algo dê errado antes do commit, podemos utilizar ROLLBACK para desfazer as alterações da transação. 

ROLLBACK;

ACID

A — Atomicidade

A transação é tratada como uma unidade: ela é efetivada ou revertida.

C — Consistência

A transação deve preservar as regras de integridade do banco.

I — Isolamento

Transações concorrentes possuem regras que controlam a interação entre elas.

D — Durabilidade

Após uma confirmação bem-sucedida, os dados devem sobreviver às condições previstas pelo sistema.

🔐 Concorrência

Em aplicações reais, várias operações podem acontecer simultaneamente.

O SGBD precisa controlar situações como:

  • Leituras concorrentes.
  • Atualizações simultâneas.
  • Locks.
  • Conflitos entre transações.
  • Deadlocks.
Objetivo:

Permitir concorrência sem comprometer a integridade dos dados.

⚡ Índices e performance

Índices podem acelerar determinadas consultas, mas possuem custos de armazenamento e manutenção. 

CREATE INDEX idx_clientes_email
ON clientes (email);

Para investigar a execução de uma consulta, podemos utilizar ferramentas como EXPLAIN. 

EXPLAIN
SELECT *
FROM clientes
WHERE email = 'ana@email.com';
Regra importante:

Performance deve ser medida e analisada. Não devemos criar índices ou alterar consultas apenas com base em suposições.

O projeto deve possuir pelo menos:

  • Tabela de clientes.

  • Tabela de pedidos.
  • Tabela de itens do pedido.
  • Primary Keys.
  • Foreign Keys.
  • Constraints apropriadas.
  • Índices relevantes.

Depois implemente:

  2. Cadastro de produtos.
  3. Criação de pedidos.
  4. Consulta de pedidos de um cliente.
  5. Consulta dos produtos mais vendidos.
  6. Soma do valor dos pedidos.
  7. Consulta de clientes que nunca fizeram pedidos.
  8. Atualização do estoque.
  9. Uma transação para registrar um pedido.
  10. Análise de pelo menos uma consulta utilizando EXPLAIN.

Uma última distinção importante

🗄️

Banco de dados

É o conjunto organizado de dados que precisa ser armazenado e gerenciado.

⚙️

SGBD

É o software responsável por gerenciar o armazenamento, acesso e operações sobre os dados.

💻

Aplicação

É o software utilizado pelos usuários ou por outros sistemas para realizar operações e utilizar os dados.

🔤

SQL

É uma linguagem utilizada para consultar e manipular dados em bancos relacionais.

SQL e NoSQL: por que estudar os dois?

SQL e NoSQL não devem ser vistos simplesmente como tecnologias concorrentes em que uma precisa substituir a outra.

Eles representam diferentes modelos e ferramentas para trabalhar com dados.

SQL NoSQL
Forte uso do modelo relacional. Pode utilizar diferentes modelos de dados.
Tabelas e relacionamentos. Documentos, chave-valor, grafos, colunas largas etc.
SQL é uma linguagem padronizada com implementações específicas. As APIs e linguagens de consulta variam conforme o SGBD.
Pode utilizar transações complexas e relacionamentos. Pode ser adequado para determinados modelos de dados e padrões de acesso.
O objetivo deste curso:

Não é decorar que "SQL é melhor" ou que "NoSQL é melhor".

É aprender a identificar as características de cada modelo e compreender quais problemas cada tecnologia pode resolver.
