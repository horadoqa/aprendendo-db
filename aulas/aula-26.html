AULA 25 • MONGODB

Relacionamentos no MongoDB

Aprenda como representar relacionamentos 1:1, 1:N e N:N usando documentos incorporados e referências.

🎯 Objetivos da aula

Na Aula 24 aprendemos que a modelagem no MongoDB deve considerar a forma como a aplicação acessa os dados.

Agora vamos estudar como representar diferentes tipos de relacionamento entre documentos.

1️⃣

1:1

Um documento relacionado a apenas um outro documento.

1️⃣

1:N

Um documento relacionado a vários outros documentos.

🔀

N:N

Vários documentos relacionados a vários outros.

🔗

Referências

Como relacionar documentos através de identificadores.

🔗 O que é um relacionamento?

Um relacionamento representa uma associação entre informações.

Por exemplo, em uma loja virtual: 

Cliente
   │
   └── possui
          │
          ├── Pedido
          ├── Pedido
          └── Pedido

Nesse exemplo, um cliente pode possuir vários pedidos.

O tipo de relacionamento depende da quantidade de elementos envolvidos em cada lado.

1️⃣ Relacionamento 1:1

Um relacionamento 1:1 significa que um documento está relacionado a apenas um documento de outro conjunto.

Um exemplo simples: 

Usuário
   │
   └── Perfil

Um usuário possui um perfil.

Opção 1 — incorporar 

{
    _id: 101,

    nome: "Ana",

    perfil: {
        foto: "ana.jpg",
        biografia: "Desenvolvedora",
        cidade: "Rio de Janeiro"
    }
}

Nesse caso, o perfil está incorporado dentro do documento do usuário.

Opção 2 — referência 

usuarios

{
    _id: 101,
    nome: "Ana",
    perfilId: 900
}


perfis

{
    _id: 900,
    foto: "ana.jpg",
    biografia: "Desenvolvedora",
    cidade: "Rio de Janeiro"
}

Aqui o perfil está separado e é relacionado através do campo perfilId.

🤔 Quando usar cada abordagem no 1:1?

Situação Incorporar Referenciar
Dados usados sempre juntos 👍 Interessante Pode ser desnecessário
Dados independentes Pode não ser ideal 👍 Interessante
Documento pequeno 👍 Interessante Também possível
Dados com regras próprias Depende Pode ser interessante

1️⃣:N Relacionamento 1:N

Um relacionamento 1:N significa que um documento pode estar relacionado a vários documentos.

Exemplos:

  • Um cliente possui vários pedidos.
  • Um professor possui várias aulas.
  • Um post possui vários comentários.
  • Uma categoria possui vários produtos. 
Cliente
   │
   ├── Pedido
   ├── Pedido
   ├── Pedido
   └── Pedido

📦 1:N com documentos incorporados

Em alguns casos, podemos armazenar os elementos relacionados dentro de um array.

Por exemplo, um produto pode possuir algumas características: 

{
    _id: 10,

    nome: "Notebook",

    especificacoes: [
        {
            nome: "Memória",
            valor: "16 GB"
        },

        {
            nome: "Armazenamento",
            valor: "512 GB"
        },

        {
            nome: "Tela",
            valor: "15.6 polegadas"
        }
    ]
}

As especificações fazem parte do contexto do produto e podem ser consultadas junto com ele.

🔗 1:N com referências

Quando a quantidade de documentos relacionados pode crescer bastante, uma alternativa é utilizar referências.

Exemplo: 

clientes

{
    _id: 101,
    nome: "Ana"
}

Pedidos: 

{
    _id: 5001,
    clienteId: 101,
    total: 3500
}


{
    _id: 5002,
    clienteId: 101,
    total: 800
}


{
    _id: 5003,
    clienteId: 101,
    total: 1200
}

O campo clienteId permite relacionar cada pedido ao cliente.

🔀 Relacionamento N:N

Um relacionamento N:N ocorre quando vários documentos podem estar relacionados a vários outros documentos.

Um exemplo clássico: 

Aluno
   ↕
Curso

Um aluno pode fazer vários cursos.

Um curso pode possuir vários alunos.

Esse tipo de relacionamento exige um pouco mais de atenção na modelagem.

Precisamos considerar como os dados serão consultados, atualizados e relacionados.

🔗 N:N usando referências

Uma possibilidade é armazenar identificadores relacionados nos documentos.

Aluno 

{
    _id: 101,

    nome: "Ana",

    cursos: [
        10,
        20,
        30
    ]
}

Curso 

{
    _id: 10,

    nome: "Banco de Dados",

    alunos: [
        101,
        102,
        103
    ]
}

Os identificadores representam os relacionamentos entre alunos e cursos.

🧩 Coleção intermediária

Em determinados cenários, pode ser mais adequado criar uma coleção específica para representar o relacionamento.

Por exemplo, uma matrícula: 

{
    _id: 9001,

    alunoId: 101,

    cursoId: 10,

    dataMatricula: ISODate("2026-02-01"),

    status: "ativa"
}

Essa abordagem é especialmente interessante quando o relacionamento possui informações próprias.

Observe:

A matrícula não é apenas uma ligação entre aluno e curso. Ela também possui data, status e outras informações.

📝 Quando o relacionamento possui dados próprios

Considere: 

Aluno
   ↓
Matrícula
   ↓
Curso

A matrícula pode possuir:

  • Data de inscrição
  • Status
  • Nota
  • Progresso
  • Data de conclusão

Nesse caso, representar a matrícula como um documento próprio pode facilitar a organização e as consultas.

🔎 E como consultar esses relacionamentos?

Em bancos relacionais, estamos acostumados com JOIN.

No MongoDB, quando utilizamos referências, podemos precisar buscar os documentos relacionados.

O MongoDB também possui recursos para realizar operações semelhantes a junções em determinadas consultas, como o $lookup. 

db.pedidos.aggregate([

    {
        $lookup: {
            from: "clientes",
            localField: "clienteId",
            foreignField: "_id",
            as: "cliente"
        }
    }

])

O $lookup permite combinar informações de coleções diferentes durante uma agregação.

Atenção:

A existência do $lookup não significa que devemos transformar todo relacionamento em uma estrutura semelhante a um banco relacional.

A modelagem continua sendo uma decisão baseada nas necessidades da aplicação.

🛒 Exemplo completo: loja virtual

Imagine três entidades: 

Cliente
   │
   └── Pedidos
          │
          └── Itens
                 │
                 └── Produto

Uma possível modelagem seria:

Cliente 

{
    _id: 101,

    nome: "Ana Silva",

    email: "ana@email.com"
}

Produto 

{
    _id: 10,

    nome: "Notebook",

    preco: 3500,

    estoque: 20
}

Pedido 

{
    _id: 5001,

    clienteId: 101,

    itens: [

        {
            produtoId: 10,
            nome: "Notebook",
            precoUnitario: 3500,
            quantidade: 1
        }

    ],

    total: 3500,

    status: "pago"
}

Observe que o pedido utiliza uma referência para o cliente e incorpora os itens necessários para representar a compra.

⚖️ Embedding x Referência

Característica Embedding Referência
Dados Dentro do documento Em documentos separados
Acesso Pode facilitar leitura conjunta Pode exigir consultas adicionais
Duplicação Pode ocorrer Pode ser reduzida
Crescimento Deve ser observado Pode lidar melhor com conjuntos separados
Complexidade Pode simplificar leituras Pode exigir combinação de dados

🧠 Uma regra prática

Ao modelar um relacionamento no MongoDB, faça algumas perguntas:

  1. Os dados normalmente são acessados juntos?
  2. O relacionamento é forte?
  3. Quantos elementos relacionados podem existir?
  4. Esse número pode crescer indefinidamente?
  5. Os dados precisam ser atualizados independentemente?
  6. O relacionamento possui informações próprias?
  7. Quais consultas serão mais frequentes?
Não existe uma regra universal.

A melhor modelagem depende do comportamento esperado da aplicação e das consultas que precisam ser realizadas.

❌ Erros comuns

❌ Incorporar tudo

Colocar todos os dados relacionados dentro de um único documento pode causar documentos grandes e difíceis de gerenciar.

❌ Referenciar tudo

Separar absolutamente tudo pode aumentar a quantidade de consultas necessárias.

❌ Ignorar crescimento

Uma estrutura pequena hoje pode crescer muito no futuro.

❌ Ignorar as consultas

A estrutura precisa considerar como os dados serão utilizados pela aplicação.

📝 Resumindo

1:1 representa uma relação entre um documento e outro.

1:N representa um documento relacionado a vários outros.

N:N representa vários documentos relacionados a vários outros.

Embedding coloca dados relacionados dentro do documento principal.

Referências conectam documentos separados através de identificadores.

Um relacionamento que possui informações próprias pode ser representado por um documento específico.

A escolha da estratégia deve considerar consultas, crescimento, atualização e comportamento da aplicação.
