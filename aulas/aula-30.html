Segurança e Boas Práticas no MongoDB

Aprenda os principais conceitos de segurança para proteger seus bancos MongoDB e evitar problemas comuns em aplicações.

🎯 Objetivos da aula

Um banco de dados pode armazenar informações extremamente importantes. Por isso, saber consultar e modificar dados não é suficiente: também precisamos saber protegê-los.

Nesta aula vamos conhecer os principais conceitos relacionados à segurança no MongoDB.

🛡️

Autorização

🔑

Credenciais

Proteger usuários, senhas e informações sensíveis.

🌐

Rede

🔐 O que significa segurança de banco de dados?

Segurança de banco de dados envolve proteger os dados contra acessos, alterações ou operações que não deveriam acontecer.

Podemos dividir o problema em algumas perguntas:

Quem pode entrar?

O que essa pessoa pode fazer?

Quais dados ela pode acessar?

Como a comunicação será protegida?

Como detectar e responder a problemas?

👤 Autenticação

Autenticação é o processo de verificar a identidade de quem está tentando acessar um sistema.

Um exemplo simples: 

Usuário:
admin

Senha:
********

O sistema verifica as credenciais antes de permitir o acesso.

Autenticação responde:

"Quem é você?"

🛡️ Autorização

Depois de identificar o usuário, precisamos determinar o que ele pode fazer.

Autorização responde:

"O que você pode fazer?"

Por exemplo:

Usuário Pode consultar Pode inserir Pode excluir
Aplicação ✅ ✅ ❌
Administrador ✅ ✅ ✅
Relatórios ✅ ❌ ❌

⚖️ Autenticação x Autorização

👤

Autenticação

Verifica a identidade.

"Quem é você?"

🛡️

Autorização

Verifica as permissões.

"O que você pode fazer?"

👥 Usuários no MongoDB

O MongoDB possui um sistema de usuários e permissões baseado em roles.

Um usuário pode receber determinadas funções que definem quais operações ele pode executar.

Conceitualmente: 

Usuário
   │
   ├── Role A
   │
   ├── Role B
   │
   └── Permissões

Isso permite separar responsabilidades e limitar o acesso de cada usuário.

🔒 Princípio do menor privilégio

Um dos conceitos mais importantes de segurança é o princípio do menor privilégio.

A ideia é simples:

Um usuário ou aplicação deve possuir somente as permissões necessárias para realizar seu trabalho.

Por exemplo, uma aplicação que somente precisa consultar informações não deveria necessariamente possuir permissão para excluir documentos. 

Aplicação de relatórios

READ
  ↓
Permitido

INSERT
  ↓
Desnecessário

DELETE
  ↓
Desnecessário

👨‍💻 Usuário da aplicação ≠ administrador

Um erro comum é utilizar o mesmo usuário com permissões administrativas para todas as operações da aplicação.

É melhor separar responsabilidades.

👨‍💼 Administrador

Responsável por tarefas administrativas, configuração e manutenção.

⚙️ Aplicação

Usuário utilizado pela aplicação, com somente as permissões necessárias.

📊 Relatórios

Usuário destinado a consultas e relatórios.

🔑 Senhas e credenciais

Credenciais de banco de dados são informações sensíveis.

Nunca devemos colocar uma senha diretamente no código da aplicação.

❌ Evite 

const password =
    "minhaSenha123";

✅ Prefira 

const password =
    process.env.DB_PASSWORD;

Variáveis de ambiente e mecanismos apropriados de gerenciamento de segredos ajudam a evitar que credenciais sejam armazenadas diretamente no código-fonte.

📁 Variáveis de ambiente

Uma aplicação pode armazenar configurações sensíveis em variáveis de ambiente. 

DB_USER=app_user
DB_PASSWORD=senha_segura
DB_HOST=localhost
DB_PORT=27017

E no código: 

process.env.DB_USER
process.env.DB_PASSWORD
process.env.DB_HOST
Importante:

O arquivo contendo credenciais locais não deve ser colocado no controle de versão de forma indevida.

🚫 Protegendo arquivos sensíveis

Em projetos que utilizam Git, arquivos com credenciais locais normalmente devem ser ignorados. 

.env

.env.local

.env.production

Um exemplo de configuração: 

# Arquivos de ambiente

.env
.env.local
.env.*.local
Atenção:

Colocar um arquivo no .gitignore não remove automaticamente um segredo que já foi publicado no histórico do repositório.

🔗 String de conexão

Aplicações normalmente utilizam uma string de conexão para informar como acessar o MongoDB. 

mongodb://usuario:senha@servidor:27017/meubanco

Em ambientes modernos, também é comum utilizar configurações fornecidas pelo ambiente de execução ou serviços de gerenciamento de segredos.

Nunca compartilhe publicamente uma string de conexão que contenha credenciais reais.

🔐 Comunicação segura

Quando dados trafegam entre a aplicação e o banco, precisamos considerar a proteção dessa comunicação.

O MongoDB suporta conexões protegidas utilizando TLS.

TLS protege a comunicação durante o transporte.

Isso é diferente de controlar quem pode acessar o banco.

🌐 Segurança de rede

Segurança não depende somente de usuário e senha.

Também precisamos controlar quem consegue chegar ao servidor MongoDB. 

Internet
    │
    │
    X
    │
Firewall
    │
    ↓
Aplicação
    │
    ↓
MongoDB

O objetivo é evitar que o banco fique desnecessariamente exposto para qualquer origem.

⚠️ Não exponha o banco desnecessariamente

Um erro grave de arquitetura é permitir que qualquer pessoa na internet consiga acessar diretamente o banco.

Em uma arquitetura comum: 

        INTERNET
            │
            ↓
        FRONTEND
            │
            ↓
       BACKEND / API
            │
            ↓
        MONGODB

O cliente normalmente conversa com a API, e a API conversa com o banco.

O navegador do usuário não deve precisar conhecer as credenciais do banco.

🏗️ Banco de dados e API

Uma aplicação web geralmente possui diferentes camadas.

🖥️

Frontend

Interface utilizada pelo usuário.

⚙️

Backend

Implementa regras de negócio e acessa o banco.

🗄️

MongoDB

Armazena os dados utilizados pela aplicação.

🚨 NoSQL Injection

Aplicações que recebem dados externos precisam validar e tratar corretamente as entradas recebidas.

Não devemos assumir que o usuário sempre enviará exatamente o formato esperado. 

Usuário
   ↓
Dados externos
   ↓
Validação
   ↓
Regras da aplicação
   ↓
MongoDB

Uma aplicação vulnerável pode permitir que entradas manipuladas alterem a lógica de uma consulta.

Nunca confie cegamente nos dados recebidos do usuário.

✅ Validação de entrada

A aplicação deve verificar se os dados recebidos possuem o formato esperado.

Por exemplo, se esperamos: 

{
    "email": "ana@email.com",
    "idade": 25
}

devemos validar:

  • Se email possui o formato esperado.
  • Se idade possui o tipo correto.
  • Se idade está dentro das regras do sistema.
  • Se campos obrigatórios foram enviados.
  • Se campos inesperados devem ser rejeitados.

🔏 Dados sensíveis

Alguns dados exigem cuidados adicionais.

🔑 Senhas

Nunca devem ser armazenadas em texto puro.

💳 Pagamentos

Podem envolver requisitos específicos de segurança e conformidade.

👤 Dados pessoais

Devem ser tratados de acordo com as regras aplicáveis ao sistema e à legislação.

🔑 Como armazenar senhas de usuários?

Uma aplicação nunca deve armazenar a senha de um usuário simplesmente como texto puro.

Em vez disso, normalmente utilizamos uma função de hash de senha apropriada, como Argon2 ou bcrypt. 

Senha informada
      ↓
Função de hash
      ↓
Hash armazenado

Quando o usuário tenta entrar novamente, a aplicação verifica a senha utilizando o mecanismo apropriado.

Hash de senha não é a mesma coisa que criptografia.

Hash é utilizado para representar a senha de forma que ela não precise ser armazenada diretamente.

💾 Backup

Segurança também significa estar preparado para perda ou corrupção de dados.

Por isso, sistemas importantes precisam de uma estratégia de backup adequada.

💾 Backup

Cópia dos dados para recuperação.

🔄 Recuperação

Processo para restaurar os dados.

🧪 Teste

Verificar se o backup realmente pode ser restaurado.

Backup que nunca foi testado não deve ser considerado uma estratégia de recuperação comprovada.

📋 Logs e monitoramento

Segurança também envolve observar o comportamento do sistema.

Dependendo da infraestrutura, podemos monitorar:

  • Tentativas de conexão.
  • Erros.
  • Operações lentas.
  • Uso de recursos.
  • Comportamentos inesperados.

Logs e métricas podem ajudar a identificar problemas e investigar incidentes.

🚀 Desenvolvimento x Produção

O ambiente de desenvolvimento costuma ser mais simples. Em produção, os requisitos de segurança são maiores.

Desenvolvimento Produção
Ambiente local Infraestrutura controlada
Dados de teste Dados reais
Configuração simplificada Segurança e monitoramento
Credenciais locais Gerenciamento seguro de segredos

✅ Checklist de segurança

Antes de colocar uma aplicação em produção, podemos fazer uma verificação básica:

  • 🔐 Autenticação está configurada.
  • 🛡️ Usuários possuem apenas as permissões necessárias.
  • 🔑 Credenciais não estão expostas no código.
  • 🌐 O banco não está desnecessariamente exposto.
  • 🔒 Comunicação segura está configurada quando necessária.
  • 🧪 Entradas externas são validadas.
  • 💾 Existe uma estratégia de backup.
  • 🔄 O processo de recuperação foi testado.
  • 📋 Logs e monitoramento estão disponíveis.
  • 🚫 Dados sensíveis não são registrados indevidamente nos logs.

Essa separação ajuda a manter as responsabilidades organizadas e evita que o cliente precise acessar diretamente o banco de dados.

❌ Erros comuns

1. Senha no código

Credenciais podem acabar expostas em repositórios.

2. Usuário com privilégios excessivos

Aumenta o impacto de um possível comprometimento.

3. Banco exposto

Aumenta desnecessariamente a superfície de ataque.

4. Dados não validados

Pode permitir comportamentos inesperados na aplicação.

📝 Resumindo

Autenticação verifica quem está tentando acessar o sistema.

Autorização determina o que esse usuário pode fazer.

O princípio do menor privilégio recomenda conceder somente as permissões necessárias.

Credenciais devem ser protegidas e não devem ficar diretamente no código.

O banco deve ser protegido também por controles de rede e comunicação segura.

Aplicações devem validar entradas externas e proteger dados sensíveis.

Backups, logs e monitoramento fazem parte de uma estratégia de segurança e recuperação.
